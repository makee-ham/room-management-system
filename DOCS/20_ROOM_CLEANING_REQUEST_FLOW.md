# 객실 청소 요청·취소 흐름

## 1. 목적

관리자는 객실의 현재 점유 상태와 관계없이 같은 위치와 같은 용어로 청소 작업을 제어한다. 사용자 화면에서는 `ON`·`OFF` 같은 구현 용어를 쓰지 않고, 실제 업무 행위인 `청소 요청`, `청소 대기열에 넣기`, `청소 취소`, `청소 진행 보기`로 표현한다.

이 문서는 객실 카드·객실 상세·청소 대기열 사이의 상태 계약과 안전 조건을 정의한다.

## 2. 모든 객실의 공통 제어

전체 121개 객실 카드는 청소 관련 버튼을 정확히 하나씩 가진다. 객실 상세도 객실번호별 청소 작업 패널을 정확히 하나 가진다. 일반 객실, 정보 확인 보류 객실, 출입·PIN 충돌 객실도 같은 제어 계약을 사용한다.

| 현재 조건 | 버튼 | 동작 |
|---|---|---|
| 요청·진행 중 청소 없음 | `청소 요청` | 확인 모달을 연다 |
| 수동 요청이 대기 중이고 아직 배정·공개·착수 전 | `청소 취소` | 취소 확인 모달을 연다 |
| 이미 예정·배정·진행·업로드·검수·재청소 중 | `청소 진행 보기` | 기존 청소 상세로 이동한다 |
| 운영 중지·정보 미확정 등 요청 차단 조건 | `청소 요청` 비활성 | 차단 사유를 버튼 설명에 표시한다 |

`청소 진행 보기`는 기존 작업을 중복 생성하지 않는다. 이미 담당이 지정되었거나 메이드에게 공개된 수동 요청도 카드에서 직접 취소하지 않고 청소 상세에서 조정한다.

## 3. 청소 요청 트랜잭션

1. 관리자가 객실 카드 또는 상세에서 `청소 요청`을 누른다.
2. 시스템은 객실번호, 점유 상태, 기존 작업, 제출·수행 회차, 운영 상태를 다시 확인한다.
3. 데이터는 아직 바꾸지 않고 확인 모달을 연다.
4. 모달은 투숙 중 객실이면 `연박 청소`, 공실이면 `추가 청소`로 등록된다는 점을 안내한다.
5. 관리자가 `청소 대기열에 넣기`를 눌러야 요청, 작업 대상, 미배정 항목, 감사 이벤트가 각각 한 번 생성된다.
6. 모달을 닫거나 상태 지문이 달라졌으면 아무 기록도 만들지 않는다.

동일 객실의 활성 수동 요청, 자동 퇴실 청소, 예정 작업, 수행 회차, 미승인 제출이 있으면 새 수동 요청을 만들지 않는다. 과거의 승인 완료 제출은 새 요청을 불필요하게 막지 않는다.

## 4. 청소 취소 트랜잭션

1. 배정 전 활성 수동 요청이 있는 객실은 `청소 취소`를 표시한다.
2. 클릭 시 데이터 변경 없이 취소 확인 모달을 연다.
3. 관리자가 모달의 `청소 취소`를 확정하면 활성 요청과 미배정 작업을 취소 상태로 닫고 감사 이력을 남긴다.
4. 요청 이전 객실 작업 상태를 복원한다.

다음 조건에서는 카드에서 취소하지 않는다.

- 청소 수행 회차가 이미 생성됨
- 미승인 제출이 존재함
- 담당 메이드가 지정되거나 통보됨
- 메이드에게 작업이 공개됨

이 경우 버튼은 `청소 진행 보기`가 되고 기존 청소 상세에서 조정한다. 과거 승인 완료 제출만 있는 경우에는 새 수동 요청의 취소를 방해하지 않는다.

## 5. 투숙 중 하위 상태

점유와 청소는 서로 배타적인 주 상태가 아니다. 투숙 중 객실의 주 상태는 계속 `투숙 중`으로 유지하고, 청소가 필요하면 하위 상태를 함께 표시한다.

```text
투숙 중
청소 필요 · 연박 청소 · 배정 준비
```

청소 단계가 바뀌면 하위 상태만 갱신한다.

```text
투숙 중
청소 필요 · 연박 청소 · 청소 중
```

청소 요청을 취소하거나 청소가 종결되면 `투숙 중`은 남고 청소 하위 상태만 사라진다.

공실 객실은 기존 퇴실 청소가 있으면 `퇴실 청소`, 수동 요청이면 `추가 청소`, 반려 뒤 다시 수행하면 `재청소`로 구분한다. 카드 버튼의 진행 문구도 실제 활성 작업 종류를 따른다.

## 6. 필터와 집계

상태 필터는 하나의 대표 상태 문자열이 아니라 실제 조건을 검사한다.

- `투숙 중`: 현재 점유 중인 모든 객실
- `청소 필요`: 점유 여부와 관계없이 현재 청소 작업이 필요한 모든 객실
- `배정 가능`: 공실이며 청소·운영·안전 조건을 충족한 객실
- `배정 불가`: 입실을 막는 운영·안전 조건이 있는 객실

따라서 같은 객실이 `투숙 중`과 `청소 필요` 양쪽에 동시에 포함될 수 있고, 상단 상태 개수의 합은 전체 객실 수보다 커질 수 있다. 화면에는 이를 `상태 중복 집계`로 명시한다.

## 7. 감사·중복 방지 원칙

- 모달을 여는 행위는 내구 원장을 변경하지 않는다.
- 확정 시 요청·대기열 항목을 각각 한 번만 만든다.
- 요청 생성·취소·현장 완료는 서로 다른 감사 이벤트로 남긴다.
- 반복 렌더링은 예약·청소·제출·수익·지급 원장을 변경하지 않는다.
- 상태가 모달을 연 시점과 달라지면 확정을 거부하고 다시 렌더링한다.
- 이미 시작된 작업을 카드의 취소 버튼으로 삭제하거나 초기화하지 않는다.

## 8. 서버 구현 시 보강할 계약

현재 와이어프레임은 브라우저 메모리 기반이다. 실제 서버 구현에서는 다음을 서버 트랜잭션으로 강제한다.

- 객실별 활성 청소 요청의 유일성 제약
- 요청 생성·취소용 멱등성 키
- 객실 상태 버전 또는 낙관적 잠금
- 서버 시각 기준 점유 판정
- 배정·공개·수행 회차·제출 상태의 원자적 취소 가능성 검사
- 감사 이벤트와 작업 원장의 동일 트랜잭션 기록
- 요청자·취소자·시각·사유 보존
