# 프런트 연결 결과와 백엔드 협의표

기준일: 2026-09-29. 사용자 확인용. 백엔드 이슈는 프런트 확인 뒤 합의한 항목만 등록한다.

## 먼저 볼 결론

기존 API로 가능한 프런트 누락을 연결했다. 남은 차이는 아래 B01~B07의 계약 문제와 실운영 UAT다. **API 호출 연결, 로컬 회귀 통과, 실제 운영 완료는 서로 다른 상태**다.

- 화면 기준: 현재 `WIREFRAME/index.html`의 역할별 정보구조와 버튼 목적. 데이터는 API adapter로 연결하며 없는 값은 추정하지 않는다.
- API 기준: 공개 OpenAPI `0.6.0`, 131 paths / 141 operations. 백엔드 main `5303fd505f18ed45fe9945d35239ccef25df2b13` (`v0.7.0`)과 대조했다.
- 기존 [문서 27](27_PRODUCT_API_IMPLEMENTATION_MATRIX.md)은 9월 28일 수정 전 기준이다. 현재 연결 상태는 이 문서가 우선한다. 제품 정책 정본 자체를 바꾸는 문서는 아니다.
- 운영 계정의 배정·사진·검수·지급 기록을 테스트 목적으로 임의 변경하지 않았다. 보호 API 쓰기 검증은 로컬 계약 fixture로 수행한다.

### 정본과 호환성

- 배정의 인라인 위/아래 화살표는 복원하지 않는다. 문서 27 F06은 과거 문서 16 표현을 잘못 가져왔다. 현재 와이어프레임/README의 자동 동선 순서가 기준이며 기존 담당·순서 변경 확인창은 유지한다.
- 새 청소는 일반 사진 1~20장이다. 이미 서버에 만들어진 구버전 작업의 슬롯은 프런트가 임의 변경하지 않는다. 기존 슬롯 API와 읽기 호환성을 유지한다.
- 디코딩 불가능한 HEIC/HEIF는 5MiB 이하 원본을 서버 정규화에 전달한다. 브라우저가 읽지 못한 원본까지 클라이언트 메타데이터 제거 완료라고 주장하지 않는다.
- 큐는 앱 메모리에만 있다. 새로고침·앱 종료 뒤 업로드/오프라인 완료 복구를 보장하지 않으며 대기 중 이탈 경고를 표시한다. 사진 원문을 기기 영속 저장소에 쓰지 않는다.
- `duration-policy` 폐기된 POST, 스케줄러 전용 예약 전이, 구형 근무 가능일 승인 절차는 새 UI로 만들지 않는다. API 수가 곧 화면 버튼 수는 아니다.

## 백엔드와 합의할 항목

### B01. 객실별 주급 산출 내역

- 사용자 상황: “어느 객실의 기본 청소비·폭탄방 가산·대기/반려가 이 금액에 포함됐나?”
- 현재: `GET /v1/payroll/entries?kind=items`의 `PayrollItem`은 `earningId`, `earnedOn`, `amount`, `alreadyClaimed` 중심이다. 집계 금액 API가 없다는 뜻은 아니다.
- 필요: 원장 행의 객실·타입·청소 종류 snapshot, 기본/가산/합계, 검수/정산 상태 및 미확정·반려·무급 재청소 조회 계약.
- 프런트: 제공된 금액만 표시. 최근 7일 사진 이력을 과거 주급에 추측 join하지 않는다.
- 합의/검수: 조회 endpoint와 필드 확정 → 일반 1건/폭탄방 1건/대기/반려/무급 재청소/이월 fixture → 관리자와 본인 메이드의 상세 합계가 집계와 일치.

### B02. 기존 조정 재정정·취소의 version

- 현재: `GET /v1/payroll/entries?kind=adjustments`의 `PayrollAdjustmentEntry`에 bookVersion이 없다. 정정/취소 명령은 최신 version을 요구한다.
- 필요: 해당 원장 CAS version을 반환하는 projection 또는 조회 endpoint. 초기값 0을 추측해서 보내면 안 된다.
- 프런트: 새로 생성해 응답 version을 아는 경우와 달리, 기존 조정의 재정정/취소는 정확한 안내와 비활성 유지.
- 검수: 두 관리자 동시 조회 → 한쪽 변경 → 다른 쪽의 낡은 version 거절 → 재조회 후 성공.

### B03. 날짜별 객실판

- 현재: `GET /v1/rooms`는 현재 상태다. `GET /v1/rooms/{roomId}/events`는 최근 50건이며 날짜별 전체 상태 재현 API가 아니다.
- 필요: 과거 일마감/미래 계획 상태 조회 범위와 기준 시각·점유·준비 상태 의미 합의.
- 프런트: 예약 달력은 사용 가능하나 현재 객실 상태를 과거/미래 확정 상태로 표시하지 않는다.

### B04. 제한 계정의 업무 찾기·재진입

- 현재: `GET /v1/limited/attempts/{attemptId}?assignmentRevision=...`와 제한 완료 API는 있다. 정확한 attempt ID/revision/capability를 알아야 한다. 일반 `auth/login`, `auth/me`는 active가 아닌 프로필에 `ACCOUNT_INACTIVE`를 반환하며 프런트는 me를 통해 부팅한다.
- 부족: 제한 사용자가 앱을 다시 열었을 때 허용된 업무 식별자를 얻는 목록/로그인 projection과 안전한 진입 계약.
- 주의: 일반 photo-slots/사진 업로드/submissions에 제한 capability 지원이 이미 일부 있다. “제한 업로드 API가 전부 없다”는 의미가 아니다. 문서 allowedActions와 실제 허용 endpoint를 함께 맞춰야 한다.
- 합의/검수: finish-only/upload-only별 로그인 → 허용 업무만 조회 → 완료/사진/제출 중 허용된 행동만 가능 → 만료·철회 후 차단. 프런트가 계정 상태를 active로 위장하지 않는다.

### B05. 미퇴실 사건의 관리자 조회 진입

- 현재: 메이드 `POST /v1/attempts/{attemptId}/checkout-not-completed`, 사건 ID를 아는 경우 `GET /v1/checkout-incidents/{incidentId}` 및 조치 명령은 있다.
- 부족: 관리자 목록 또는 room/target에서 incidentId를 알아내는 조회. AssignmentCard/lifecycle-impact에 incidentId가 없고 알림 deepLink에도 incident 종류가 없다.
- 프런트: 미퇴실 신고는 연결돼 있지만 다른 사용자가 신고한 사건을 관리자가 항상 발견해 해결하는 전체 흐름은 미완료. 문서 27 C08의 ‘연결’ 표기는 이 범위를 과대평가했다.
- 합의/검수: 메이드 신고 → 다른 관리자 세션에서 사건 발견 → 단건 상태/허용 조치 확인 → CAS 조치 → 청소/예약 상태 갱신.

### B06. 새 사진 템플릿 OpenAPI 일치

- 현재: `POST /v1/cleaning-templates` 구현은 일반/폭탄방/특이사항 3슬롯을 허용하지만 공개 `PublishCleaningTemplateRequest.slots`는 `minItems: 9`, `maxItems: 14`가 남아 있다.
- 필요: 새 3슬롯과 기존 템플릿 호환 조건을 schema/생성 타입/계약 테스트에 동일하게 반영.
- 참고: GET 응답은 `templates.roomTypes`다. 프런트가 그 실제 응답 형태를 사용하도록 수정했다.
- 검수: 설정 없는 타입 expectedVersion=0 발행 → 새 작업 3슬롯 생성 → 일반 0장 제출 거절, 1/20장 허용, 21장 차단.

### B07. 제출 전 폭탄방·특이사항의 관리자 조회

- 현재: 관리자 lifecycle-impact로 수행 상태는 알 수 있다. 일반 `attempts/current`와 `attempts/{id}/submissions`는 메이드 본인용이고, 관리자 검수 상세는 제출 이후에 열린다.
- 부족: 제출 전 신고를 관리자 객실 상세에서 조회하는 projection. `room issues` 운영 이슈 목록과 메이드의 청소 증빙 신고는 동일 리소스가 아니다.
- 프런트: ‘신고 없음/0건’으로 추정하지 않고 제출 전 신고 조회 API 미제공 표시. 제출 후 실제 사진·메모는 검수 상세에서 조회.
- 합의: 제출 전부터 관리자 확인이 필요한지 결정 → 필요하면 해당 신고의 조회 권한/사진 보존 범위 정의.

### 함께 확인할 계약 정합성

- PIN 전체 재동기화 응답 `roomCount: const 121`은 동적 객실 등록/비활성 API와 맞춰야 한다. 완료를 검증할 catalog/PIN revision 또는 행 수 기준도 확인. 202는 접수일 뿐 Drive 반영 완료가 아니다.
- `payrollProfile` 알림에는 주차가 없다. 특정 과거 지급을 열어야 하면 `payrollCycle` 또는 명시적 weekStart가 필요하다. 현재 cycle 알림은 정확한 주차를 복원한다.
- 사진 7일은 승인/반려 기준 보존과 실제 Drive purge 성공까지 별도 운영 확인한다. UI에서 7일 조회된다는 사실만으로 원본 삭제까지 검증했다고 하지 않는다.

## 회의 순서

1. 배포 화면에서 관리자/메이드의 주요 동선을 확인한다.
2. B01~B07을 보며 ‘필드 추가 / 조회 진입 추가 / 정책 확인 / 문서만 수정’ 중 처리 방향과 담당을 정한다.
3. 테스트용 메이드·객실·예약·업무를 지정한다. 실제 운영 청소나 지급 기록은 임의 변경하지 않는다.
4. 실제 사진 업로드 → 현장 완료 → 제출 → 폭탄방 판정 → 승인/반려 → 주급 반영 → 이력 조회를 양쪽 계정에서 확인한다.
5. 프런트 컨펌 후 합의한 차이만 이슈로 올린다. 이 문서의 B ID, endpoint/schema, 재현 절차와 기대 결과를 함께 넘긴다.

## 검증 근거와 한계

실행 결과와 대표 스크린샷은 [QA](../WIREFRAME/QA.md)의 2026-09-29 절에 기록한다. 로컬 브라우저 검증은 운영 모드 UI에 계약 fixture를 연결한 검사이며 운영 DB를 수정하지 않는다.

실기기 Android/iOS 갤러리·카메라·설치 앱 Back, 실제 Drive 업로드/만료 삭제, Push 도착, 다중 관리자 동시 변경, 실제 계정 제한 전환과 지급 기록 UAT는 별도다. 금융 작업은 외부 송금이 아니라 기록 API이며 실제 송금을 테스트로 실행하지 않는다.
